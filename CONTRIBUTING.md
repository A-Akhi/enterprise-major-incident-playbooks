# Contributing

Thank you for helping improve these operational playbooks. Contributions should make guidance easier to use under pressure, while remaining adaptable to different organizations and platforms.

## Good contributions

- Add or improve incident command checklists, escalation paths, communication templates, and retrospective practices.
- Clarify roles, decision points, assumptions, and handoffs.
- Include practical examples only when they are clearly illustrative and do not expose real customer, employee, or system information.
- Link related material elsewhere in this repository rather than duplicating it.

## Documentation conventions

- Use Markdown and descriptive, lowercase, hyphen-separated filenames for new documents.
- Keep headings concise and use checklists, tables, or short numbered steps where they improve scanability.
- State the intended audience, trigger or use case, and any prerequisites near the beginning of a playbook.
- Define acronyms on first use and use UTC for example incident timelines.
- Make owners, approval requirements, and follow-up actions explicit. Avoid presenting illustrative targets as universal requirements.
- Keep links relative to the repository so they work in forks and local clones.

## Before submitting

- Check spelling, Markdown rendering, and all internal links.
- Confirm that examples contain no secrets, personal data, customer data, or sensitive operational details.
- Ensure recommendations do not conflict with the document’s stated security, evidence-preservation, or change-approval requirements.
- Explain the intended audience and operational benefit in your pull request description.
